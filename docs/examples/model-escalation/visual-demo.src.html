The move

Same credential, same endpoint — only the model field changes

Spending a found key on a different provider is key theft. Spending it on a stronger model at the legitimate provider is model escalation: same credential, same endpoint, one field. The September 2026 benchmark made the move famous — the model outsourced part of its task to stronger models and outscored itself.

No boundary

The client's config owns the model list — and it is honored

Side A runs the agent image as a plain container: a provider key in the environment, unrestricted network, a stand-in provider on the host playing the real provider's role. The client-side model list is the user's own config file — the user who owns the config owns the list.

The choice was honored verbatim, the key traveled with every request, and nothing refused or logged a violation. A real provider would bill for this and tell no one.

The mechanism

The model field is a lookup key, not a command

Behind the boundary, every path to a model runs through the Praxis gateway. Its unified model catalog answers /v1/models from the administrator's configuration, and the request's model field is checked against it before credentials are injected.

The fallbacks

The same pick, three ways — all refused

Side B tries the escalation three ways: in the request body, forged into the routing header, and by skipping the gateway entirely.

The sanctioned flow

The approved model answers

The demo's sanctioned pick is a budget model — the budget-versus-premium tiering an administrator would actually configure. Through the catalog it works exactly as intended:

side B, through the catalog

the approved model answered: I am the GPT-4.1-mini language model.

Side B makes exactly one real completion request — the sanctioned model, a few tokens. The wrong-model requests are refused before credentials, and no key ever exists inside the sandbox to transmit.

What this demo does not claim

The catalog decides which — not how much

scope
  • The catalog is per-gateway. Every sandbox behind one gateway shares the routable set; per-agent tiers are a deployment pattern, not something this demo demonstrates.
  • The client contract constrains the catalog. The deployed client path sends the legacy max_tokens parameter, which current premium families reject; the sanctioned model must be one the qualified client can actually call.
  • Quota and audit are the spend controls. The catalog decides which models are routable; rolling-day token limits and per-request access logs decide and record how much.

What to remember

Agents may use only the models the administrator approved

  1. The model field is a catalog lookup key, not a command. The gateway refuses unknown models with a static 404 before credential injection.
  2. The refusal happens where the credential lives. No provider key exists inside the sandbox, so there is nothing to spend on any model.
  3. Headers do not route. Caller copies of X-Gateway-Model are stripped during body pre-read; the body's model decides.
